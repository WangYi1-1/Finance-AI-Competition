# 从一个数字开始读代码

先运行演示，再选一个指标核对整个路径。建议先看“营业收入”：PDF 原文里写了什么，程序保存了哪些字段，统一金额如何得到，为什么会进入或退出期间比较。这样读代码，每一步都能在界面上看到对应结果。

## 第一步：看懂数据结构和一个金额

打开 `finance_agent/schemas.py`，先读 `Evidence` 和 `Metric`。

`Evidence` 是原文片段，包含文件名、从 1 开始的 PDF 页序号、文本与坐标；表格证据还保留单元格。`Metric` 是一个财务数字，除了金额，还保存公司、期间、原始金额、单位、合并或母公司口径、累计或单季度类型、引用编号、数值所在的原文行和校验状态。行列位置用于检查数字是否对应模型声称的指标和期间。

假设原文在一个“单位：万元”的表里写着“营业收入 12,500.00”。程序应保留 `raw_value="12,500.00"`、`unit="万元"`，统一金额为 `125000000.00` 元。这里使用 `Decimal`，因为它能按十进制精确表示金额，避免普通浮点数的二进制近似。

```python
from decimal import Decimal

raw_value = "12,500.00"
value_in_yuan = Decimal(raw_value.replace(",", "")) * Decimal("10000")
assert value_in_yuan == Decimal("125000000.00")
```

练习只做三件事：找到对应证据编号；在原 PDF 页确认数值和单位；查看 `result.json` 的金额是否一致。“核验通过”表示程序做过规定检查，数字是否来自正确列、期间和口径仍需要核对。

## 第二步：找出模型和程序各自做了什么

顺着下面的调用路径读，每次只打开一两个文件：

```text
app.py / cli.py
    → pipeline.py
        → parser.py      PDF → 带页码的原文片段
        → extraction.py  原文片段 → 指标与披露 → 核验 / 补查
            → llm.py     调用 DeepSeek 并处理失败
        → comparatives.py 原表明确对比列 → 配对检查 → 原文核验
        → analysis.py    核验后的数据 → 比较与信号
        → 输出文件
```

`parser.py` 先按页读取原文，再用关键词选择可能包含报表和附注的片段。每个片段拥有固定引用编号。模型收到的是这些片段，而不是默认收到整份年报。

`extraction.py` 把模型返回的 JSON 转为 `schemas.py` 规定的结构，检查金额、原文行和引用，并根据失败反馈最多补查一次。校验函数才会将指标标为 `verified`；手动构造一个字段齐全的对象，不能代替这一过程。`llm.py` 只负责官方接口、重试与用量，财务规则不放在里面。

模型负责理解“这是归母净利润还是合并净利润”“这段附注是否说明政策变化”。Python 负责单位换算、变化率、口径比较和规则判断。一个 JSON 形状正确，仅能说明它符合字段要求，不能证明它的财务含义正确。

`comparatives.py` 再检查财报原表中是否存在模型漏提的对比金额。以已经核验的本期金额为锚点，确认同表同期间的金额一致，再按明确列头核验基期金额。遇到模糊日期、单位不明确或数值冲突，就保留缺失；不能由财报披露的增长率反推金额。

## 第三步：看一条同比

在 `analysis.py` 中找到期间比较代码。对本期和基期分别追踪公司、指标、期间起止、报表口径、是否调整和校验状态。只有它们可比，才执行：

```text
增减金额 = 本期金额 - 基期金额
普通变化率 = 增减金额 / 基期金额 × 100%
```

基期为零、负数或接近零时，结果应该告诉用户原因。半年累计值与一季度累计值不能直接作为相邻单季度比较。应收账款、存货、资产总额是某一天的余额，不应按累计流量的方法相减来推导季度值。

练习：先找到演示中的一个同比结果，手算检查，再看它引用了哪两份原文。之后阅读对应测试里的零基期、负基期和口径不一致案例。

## 第四步：看一条异常信号

先读“利润与经营现金流背离”。它应匹配同公司、同期间的合并净利润与合并经营现金流，保存参与判断的金额和原文来源。出现信号后，附注中的应收账款、存货或季节性解释用于进一步核对。

把 `Signal.status` 的三个状态看清楚：发现信号、在已检查范围内未发现信号、证据不足。没有找到相关披露时，需要的是补查或待核实状态。会计政策变化和非经常性损益也需要同样的证据检查。

这一步的练习是先查看某张信号卡片的 `details`，再点击原文依据。确认读者可以依据这两部分复核规则为什么触发。

## 第五步：理解你之前学过的反馈循环

这里的流程可以对应你学过的 Agent 循环：

```text
提取 → 程序核验 → 得到问题反馈 → 补查 / 重新提取 → 再核验
```

例如模型声称营业收入是 12,500.00，但引用的营业收入原文行只有 12,000.00，程序可以指出金额无法核实，再将这个问题反馈给模型。单位换算由程序依据原始金额重新计算；模型给出的统一金额不直接用于运算。无法解决时保留待核实状态。第一版采用固定流程并最多补查一次，便于逐步理解与定位问题。

查看一次运行的 `trace.jsonl`，先找 PDF 解析，再找模型请求和响应，最后找核验与财务分析。它记录可见输入输出，不是模型内部思考过程，也不保存 API 密钥。

## 接下来怎么改

你先完成上面的一个金额练习。下一次修改只挑一个真实财报出现的问题：缺少一种指标别名、某种表格单位不清楚、或一种比较口径需要拒绝。先写清楚原文、期望结果和当前结果，再改对应模块，最后用这个真实案例验证。

暂时不要同时修改解析、提示词、财务规则和界面。让一次修改对应一个问题，后面写比赛报告和解释代码会更容易。
